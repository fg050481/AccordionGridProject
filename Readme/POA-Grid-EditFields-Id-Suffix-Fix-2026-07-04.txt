 POA FORM MANAGEMENT — ACCORDION GRID
 FIX: Edit-mode dropdowns show wrong values (Id-suffix key mismatch)
 Date: 2026-07-04
═══════════════════════════════════════════════════════════════════════════════


───────────────────────────────────────────────────────────────────────────────
 1. THE BUG — WHAT IS HAPPENING AND WHY
───────────────────────────────────────────────────────────────────────────────

SYMPTOM
  • View mode (arrow expand)   → shows CORRECT values
  • Edit mode (Edit button)    → every dropdown shows the FIRST option
    (FULL SERVICE / POA for Signature / New POA / AL / Missoula Office…)
  • console.log of the record  → data from server is CORRECT

ROOT CAUSE
  Each record coming from GetPage carries TWO properties per lookup field:

      ServiceType:        "ADP - UCM"         ← display string (no suffix)
      ServiceTypeId:      8                   ← numeric FK    (Id suffix)
      FormType:           "Online Instructions"
      FormTypeId:         2
      FormUse:            "Rescind POA"
      FormUseId:          2
      PoaType:            "Benefit and Tax"
      PoaTypeId:          3
      SignatureType:      "Wet by Registered Officer"
      SignatureTypeId:    2
      ReturnType:         "Hard Copy Completed Form Mailed to Mailroom"
      ReturnTypeId:       2
      OnlineRequirement:  "Assign as TPA - We follow up"
      OnlineRequirementId: 1

  EXCEPTION — Mail Center has the naming INVERTED on the backend:

      MailCenterId:       "Londonderry Office"   ← the STRING got the Id name
      MailCenterIdInt:    2                      ← the INT got pushed to IdInt

  The editFields config keys point at the STRING properties (no suffix).
  The dropdown option lists carry NUMERIC FK values (1, 2, 3, …).

  So when the edit panel renders a <select>:

      String(option.value) === String(record[field.key])
      String(8)            === String("ADP - UCM")        → never true

  No <option> gets marked selected, so the browser silently defaults every
  select to its FIRST option. No error is thrown anywhere.

WHY VIEW MODE LOOKS CORRECT (this is the trap)
  buildViewFieldHtml does the same failed option-match, BUT it has a
  fallback:

      display = match ? match.label : escapeHtml(val);   // ← fallback

  When no option matches, it prints the raw value verbatim — and the raw
  value IS the human-readable string ("ADP - UCM"). So view mode is
  ACCIDENTALLY correct: it never resolved the lookup at all, it just echoed
  the string. That is why the bug only surfaces in edit mode.

THE FIX (one sentence)
  Point every select-type editField key at the numeric ...Id property, and
  update every other place that references those keys by string.

CRITICAL RULE
  editField keys are plain strings matched EXACTLY in multiple places.
  There is no compiler check. A rename missed in one place fails silently
  (field disappears from its section, or DTO sends null). Rename EVERYWHERE.

 5. CHANGE #4 — CLEAN MAILCENTER FIX (BACKEND: flattener + DTO + repo)
───────────────────────────────────────────────────────────────────────────────

PROBLEM
  Every lookup field follows the convention:
      <Name>        = display string   (ServiceType = "ADP - UCM")
      <Name>Id      = numeric FK       (ServiceTypeId = 8)
  Mail Center is the ONE inverted exception:
      MailCenterId     = display string  ("Londonderry Office")  ← WRONG
      MailCenterIdInt  = numeric FK      (2)                     ← WRONG
  This forces a special case in the frontend and will keep biting anyone who
  touches this page. Fix the names at the source so ALL fields follow the
  same convention.

TARGET CONVENTION
      MailCenter    = "Londonderry Office"    (string, no suffix)
      MailCenterId  = 2                       (int FK, Id suffix)

──────────────── 5a. GetPage flattener (WebMethod, code-behind) ──────────────

BEFORE (from the .Select projection):
        x.MailCenterId,          // string  "Londonderry Office"  ← misnamed
        x.MailCenterIdInt,       // int     2                     ← misnamed

AFTER:
        MailCenter = x.MailCenterId,        // temp: read old model prop into new name
        MailCenterId = x.MailCenterIdInt,   // temp: read old model prop into new name

  …or, once the model/repo props are also renamed (5c), simply:

        x.MailCenter,            // string
        x.MailCenterId,          // int

──────────────── 5b. PoaFormDto ─────────────────────────────────────────────

BEFORE:
        public int? MailCenterId { get; set; }
        // (if a string MailCenterId or MailCenterIdInt variant exists, remove it)

AFTER:
        public int? MailCenterId { get; set; }   // int FK — the only one the DTO needs

  The DTO only ever needs the FK int for insert/update. The display string
  is a read-path concern (flattener) — it should NOT be on the DTO at all.

──────────────── 5c. Repository / model projection ──────────────────────────

Wherever GetAllForms projects the mail center (the repo/service .Select):

BEFORE:
        MailCenterId    = mc.mail_center_description,    // string in Id-named prop
        MailCenterIdInt = pf.mail_center_id,             // int in IdInt prop

AFTER:
        MailCenter   = mc.mail_center_description,       // string, no suffix
        MailCenterId = pf.mail_center_id,                // int FK, Id suffix

And on the model class:

BEFORE:
        public string MailCenterId    { get; set; }   // display string  ← misnamed
        public int?   MailCenterIdInt { get; set; }   // FK int          ← misnamed

AFTER:
        public string MailCenter   { get; set; }      // display string
        public int?   MailCenterId { get; set; }      // FK int

──────────────── 5d. Insert/Update mapping (server) ─────────────────────────

Wherever the entity is built from the DTO — no change needed IF it already
reads form.MailCenterId as an int:

        mail_center_id = form.MailCenterId,       // stays the same

  Just confirm nothing was parsing the old string prop.

──────────────── 5e. Search the solution for stragglers ─────────────────────

Grep the whole solution (C# and JS) for:
        MailCenterIdInt
Every hit must be renamed or removed. When the grep returns ZERO results,
the inverted naming is fully gone.
